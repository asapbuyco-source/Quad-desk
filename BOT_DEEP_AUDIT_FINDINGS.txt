Current Blocking Findings
-------------------------

P0. Live startup can crash because _task_death_callback is referenced before definition
File: bot/main.py:3065-3070 and bot/main.py:3171

Problem:
The user-data stream task is created and _uds_task.add_done_callback(_task_death_callback)
is called before _task_death_callback is defined later in main().

Impact:
In live mode with BINANCE_API_KEY set, startup can fail before the bot reaches the
main task list. This is a live-path blocker.

Suggested fix:
Move the _task_death_callback definition above any create_task/add_done_callback
usage, or delay user-data stream task creation until after the callback is defined.
Add the user_data_stream task to the main tasks list for clean shutdown.


P0. Breakeven CVD branch uses side before assignment
File: bot/executor.py:1209-1228

Problem:
check_breakeven_and_partials() now accepts metrics, but the CVD branch checks
side at lines 1213-1215 before side is assigned at line 1228.

Impact:
If metrics contains cvd_divergence with strength > 0.40, this path can raise
UnboundLocalError and break breakeven handling.

Suggested fix:
Assign entry_price and side immediately after pos is loaded, before the metrics
CVD branch.


P1. User-data stream task is supervised but not included in shutdown tasks
File: bot/main.py:3065-3070 and bot/main.py:3198-3212

Problem:
The user-data stream task gets a done callback, but it is not stored in the tasks
list that is later cancelled and awaited during shutdown.

Impact:
Shutdown can leave the stream task outside the normal cleanup flow.

Suggested fix:
Create _uds_task = None before task creation, append it to tasks if created, and
cancel/await it with the rest.


P1. Duplicate live-entry race remains open
File: bot/executor.py:587-758 and bot/executor.py:812-844

Problem:
The lock protects preflight checks but is released before live market order
placement. pending_order is only set after create_market_order() returns.

Impact:
A second concurrent signal path can pass the no-position/no-pending checks while
the first live order is in flight.

Suggested fix:
Set an entry_in_progress or pending_order sentinel inside _position_lock before
releasing it for exchange calls. Clear or update it once the entry succeeds/fails.


P1. Risk ledger is still memory-only
File: bot/main.py:154-166 and bot/main.py:2318-2359

Problem:
daily_pnl, session_pnl, cumulative_pnl, daily_loss_halt, and drawdown_halt still
live only in BOT_STATS process memory.

Impact:
A restart or redeploy can reset loss controls and bypass daily/cumulative halt
state.

Suggested fix:
Persist a risk ledger to Firestore/local durable state:
- date-scoped daily_pnl and daily_loss_halt
- cumulative_pnl
- drawdown_halt
- last update timestamp

Load it during startup before trading begins.


P1. WebSocket fill callback now clears active_position, but needs idempotency guard
File: bot/main.py:3054-3063

Problem:
The callback now clears executor.active_position after _process_exit(), which fixes
the earlier double-count risk in the normal case. However, there is no explicit
exit idempotency key or last-processed order/trade id.

Impact:
Duplicate ORDER_TRADE_UPDATE messages, reconnect replay, or a near-simultaneous
poll event can still double-process an exit if timing is unlucky.

Suggested fix:
Track last processed close order id / trade id / event id, or store an
exit_processed flag on the position before awaiting _process_exit().


P1. Protective futures order params still need Binance testnet verification
File: bot/executor.py:910-916 and bot/executor.py:930-936

Problem:
STOP_MARKET and TAKE_PROFIT_MARKET orders pass closePosition=True while also
passing amount. A nearby comment says reduceOnly works with amount and
closePosition does not.

Impact:
Protective orders may be rejected or behave differently than expected depending
on CCXT/Binance behavior.

Suggested fix:
Verify on Binance USDM testnet. Use either:
- closePosition=True without amount, or
- reduceOnly=True with amount

Document the chosen behavior with a testnet transcript or integration test.


P2. Spot aggTrade vs USDM futures tape mismatch remains
File: bot/data_feed.py:145-148

Problem:
The bot executes USDM futures, but CVD/tape comes from Binance Spot aggTrade.

Impact:
Spot flow may diverge from futures flow during liquidation, funding, and basis
events.

Suggested fix:
Make this explicit in config and telemetry, or prefer futures aggTrade with a
fallback to spot only when futures aggTrade is unhealthy.


P2. Test coverage is still too narrow
File: tests/test_executor.py

Problem:
Existing tests pass but only cover a small slice of executor behavior.

Missing tests:
- live startup with user-data task enabled
- TP failure after market fill and SL success
- duplicate-entry prevention while first order is in flight
- breakeven CVD branch
- watchdog continues after first aggTrade warmup
- listen-key keepalive refresh
- risk-ledger persistence/load
- WebSocket fill idempotency

Impact:
The most important live fixes are not protected against regression.
