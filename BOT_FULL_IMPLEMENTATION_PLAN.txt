P0-1. Fix _task_death_callback definition order
------------------------------------------------
Problem:
bot/main.py uses _task_death_callback before it is defined.

Current evidence:
- Used at bot/main.py:3160:
  feed._uds_task.add_done_callback(_task_death_callback)
- Defined later at bot/main.py:3261.

Impact:
In live mode with BINANCE_API_KEY set, main() can fail at startup before the main
bot task group is created.

Implementation:
1. Move the _task_death_callback function above the user-data stream creation block.
2. Keep user-data stream task creation after callback definition.
3. Keep feed._uds_task in the shutdown tasks list.
4. Avoid creating any task with add_done_callback before the callback exists.

Target structure:
    def _task_death_callback(task: asyncio.Task):
        ...

    if not DRY_RUN and BINANCE_API_KEY:
        feed._uds_task = asyncio.create_task(
            feed.run_user_data_stream(BINANCE_API_KEY, _on_ws_fill),
            name="user_data_stream",
        )
        feed._uds_task.add_done_callback(_task_death_callback)

Acceptance criteria:
- Live startup path with BINANCE_API_KEY set does not raise NameError or
  UnboundLocalError.
- user_data_stream appears in the shutdown task list if it was created.
- py_compile passes.

Tests to add:
- A source-order regression test that asserts the first occurrence of
  "def _task_death_callback" appears before the first "add_done_callback(_task_death_callback)".
- Optional async startup smoke test with mocked feed/executor.

P0-5. Add idempotency guard to _process_exit
--------------------------------------------
Problem:
Multiple paths can process the same exit:
- user-data stream callback
- 30s heartbeat/live position poll
- main loop check_position_exit

_process_exit currently increments daily_pnl, session_pnl, cumulative_pnl and
updates win-rate state without a duplicate guard.

Current evidence:
- bot/main.py:2387 defines _process_exit.
- bot/main.py:2401-2403 increments PnL directly.
- No closed_trade_ids or processed_exit_ids guard found.

Impact:
One trade close can be counted twice. This can corrupt:
- daily_pnl
- session_pnl
- cumulative_pnl
- daily_loss_halt
- drawdown_halt
- Bayesian priors
- consecutive loss cooldowns

Implementation:
1. Add an idempotency set to BOT_STATS:
       "closed_trade_ids": set()
2. At the top of _process_exit, snapshot the active position:
       pos = executor.active_position or {}
       doc_id = pos.get("trade_doc_id", "")
3. If doc_id is already in stats["closed_trade_ids"], log and return.
4. If doc_id exists and is new, add it before any await or state mutation.
5. If doc_id is missing, use a fallback key from order id, symbol, side, and a
   close timestamp bucket only if needed.
6. Reset closed_trade_ids on daily reset, or keep a bounded deque/set of recent
   processed IDs to avoid unbounded memory growth.

Acceptance criteria:
- Two rapid calls to _process_exit for the same trade only increment PnL once.
- _process_exit remains safe if trade_doc_id is absent.
- Existing risk-ledger save still runs after a legitimate first exit.

Tests to add:
- Duplicate _process_exit call with same trade_doc_id.
- Two different trade_doc_ids both process normally.
- Missing trade_doc_id path does not crash.


P0-6. Fix derivatives cache first-boot behavior
-----------------------------------------------
Problem:
_DERIV_CONTEXT_LAST_UPDATE starts at 0.0. On first _compute_signal call,
age is approximately current epoch seconds, so the code treats cache as extremely
stale and bypasses the derivatives gate until the background task fetches data.

Current evidence:
- bot/main.py:302 sets _DERIV_CONTEXT_LAST_UPDATE = 0.0.
- bot/main.py:2201 computes age.
- bot/main.py:2203 logs stale cache and bypasses derivatives gate.

Impact:
For the early boot window, derivatives veto is skipped. The downloaded audit calls
this out correctly.

Implementation:
1. Add explicit warming state:
       _DERIV_CONTEXT_WARMING = True
2. In _derivatives_refresh_loop, perform first fetch immediately or after a very
   short delay, then set _DERIV_CONTEXT_WARMING = False after success.
3. In _compute_signal:
       if _DERIV_CONTEXT_WARMING:
           log INFO "[DerivGate] warming - skipping"
           skip derivatives gate without WARNING
       elif cache age > 900:
           log WARNING and bypass as stale
       else:
           apply derivatives gate normally
4. Do not confuse first-boot warming with stale production data.

Acceptance criteria:
- First boot logs "warming" rather than "STALE_CACHE_BYPASSED".
- After first successful fetch, derivatives gate applies normally.
- If cache later becomes older than 900s, stale warning still appears.

P1-2. Normalize confidence after each stage and before Kelly sizing
-------------------------------------------------------------------
Problem:
Confidence is modified by several pipeline stages:
- CVD gate
- Bayesian fusion
- VPOC boost
- ULIS boost/veto/penalty
- alignment penalties

Some clipping exists, but it is inconsistent. Confidence is later used in Kelly
sizing.

Current evidence:
- VPOC uses min(1.0, confidence + vpoc_boost) in bot/main.py:2263.
- ULIS gate modifies confidence in _apply_ulis_gate.
- execute_signal uses _kelly_scale(confidence, rr) in bot/executor.py:661.

Impact:
Inflated confidence can oversize trades. Negative or >1 confidence can distort
logs, thresholds, and Kelly.

Implementation:
1. Create helper:
       def _clamp_confidence(value: float) -> float:
           return float(np.clip(value, 0.0, 1.0))
2. Apply after every confidence modification in _compute_signal and _apply_ulis_gate.
3. Before execute_signal, assert/log:
       if not 0.0 <= confidence <= 1.0:
           logger.error(...)
           confidence = _clamp_confidence(confidence)
4. In TradingExecutor.execute_signal, defensively clamp confidence before Kelly.

Acceptance criteria:
- Confidence logged in "[Signal] >>" is never outside [0, 1].
- Kelly receives only clamped values.
- Unit tests cover extreme confidence inputs.


P1-3. Fix HMM cold-start regime commit after seeding
----------------------------------------------------
Problem:
The HMM seeding block commits the current _candidate_regime after processing the
last few seed candles. This can overreact to the final seed candle.

Current evidence:
- bot/main.py:3194 iterates over rest_candles[-5:].
- bot/main.py:3198 sets _committed_regime = _candidate_regime.

Impact:
Bot can begin live trading in a regime caused by a single transitional/spike
candle instead of the modal recent regime.

Implementation:
1. During the last-five-candle seed pass, collect raw regimes.
2. Use Counter(...).most_common(1)[0][0] to pick the modal boot regime.
3. Set both _committed_regime and _candidate_regime to that mode.
4. Set _candidate_streak to HYSTERESIS_CANDLES.
5. Clear _obs_buf after this as currently intended.

Acceptance criteria:
- A seed sequence with four RANGE candles and one final TREND spike commits RANGE.
- Hysteresis state is consistent after boot.

P2 - Model Validity and Architecture
====================================

P2-1. Improve backtest/live parity
----------------------------------
Problem:
The downloaded audit correctly notes that backtest_hybrid.py is not equivalent to
live bot logic. Live uses real aggTrade CVD, order book walls, Amihud, HMM features,
and more detailed gates.

Implementation phases:
1. Ensure backtest CVD uses taker_buy_base:
       delta = (2 * taker_buy_base) - total_volume
       cvd += delta
       reset daily
2. Add Amihud proxy from kline data:
       illiq_raw = abs(close - open) / (volume * close + eps)
       rank over rolling window
3. Extract _HMMRegimeClassifier from main.py into a dedicated module so live and
   backtest can import the exact same classifier.
4. Use the same regime params and signal config in backtest.
5. Keep wall proxy if historical LOB is unavailable, but document limitations.

Acceptance criteria:
- Backtest logs regime distribution.
- Live and backtest call the same regime classifier.
- Backtest results are marked invalid unless parity checks pass.


P2-2. Add confidence calibration logging and Kelly gate
-------------------------------------------------------
Problem:
Kelly sizing assumes confidence approximates P(win). This is not proven.

Implementation:
1. Ensure trade records include signal confidence at entry.
2. On exit, write:
       result = WIN/LOSS
       calibration_bucket = round(confidence * 10) / 10
3. Add a calibration summary script:
       bucket -> realized win rate, count, avg pnl
4. Disable or cap Kelly until each bucket has enough evidence.
5. Add config:
       KELLY_ENABLED = False by default for live
       MIN_CALIBRATION_TRADES = 20

Acceptance criteria:
- Kelly multiplier cannot increase size unless calibration evidence exists.
- Calibration report can be generated from Firestore botTrades.
